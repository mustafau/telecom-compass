# Interface contracts

`answer.schema.json` describes the persisted/browser envelope. Create a Zod equivalent and assert schema parity in tests. It is not sufficient by itself for authorization or grounding.

[domain-types.ts](domain-types.ts) specifies the normalized resource, pagination, diagnostic and evidence shapes. Its optional fields are deliberate. `relationsComplete=false` means that an empty relation array cannot establish absence. Create API/version-specific raw parsers, then map to these domain shapes; do not serialize raw TMF entities directly as tool outputs. Final projection may remove more fields for the current audience.

Runtime rules beyond JSON Schema:

- Envelope identity/time/environment fields are generated by the server.
- Observations, inferences and domain guidance require one or more authorized current-turn evidence IDs. A clarification can have none; a capability limitation comes from trusted capability metadata, not a fabricated evidence record.
- Every evidence ID belongs to the same tenant, deployment, conversation, turn and permitted audience.
- Each card field references a normalized evidence JSON pointer and must equal its source value or an explicitly registered formatter (for example UTC-to-display-time conversion). Model-authored arbitrary transforms are forbidden.
- The server constructs card IDs/titles/labels from a whitelist for their kind. The schema's generic fields permit evolution, not arbitrary disclosure.
- `answered` requires at least one supported claim; `partial` includes gaps; clarification includes a specific question. Empty output is invalid at the application layer.
- Final status and scope are validated against actual tool outcomes; a model cannot hide a failed required lookup by claiming completeness.
- Raw source URLs, provider messages, internal prompts and tool credentials are never part of this contract.

HTTP contracts are maintained in the [API design](../api-and-streaming.md). Implement request schemas in src/contracts and generate API documentation from those schemas when practical; do not keep two divergent definitions.
